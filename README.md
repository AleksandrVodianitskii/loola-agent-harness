# Loola Coding Agent Harness

Харнесс для OpenAI-совместимого Chat Completions API. Скиллы загружаются по запросу, а история сжимается при приближении к лимиту контекста. Python 3.10+, без сторонних зависимостей.

## Запуск

```sh
export LLM_BASE_URL=https://your-provider.example/v1
export LLM_MODEL=your-model
# При необходимости задайте LLM_API_KEY в окружении.
python3 -m harness --workspace ./project --context-window 8192 --json \
  "Проверь файлы проекта и сохрани краткий отчёт в report.md"
```

`--context-window` задаёт полное окно модели. `--max-output-tokens` резервирует место для ответа. Для OpenAI-совместимых серверов, ожидающих другой параметр, передайте `--output-token-field max_completion_tokens`. Для серверов с поддержкой `prompt_cache_key` можно задать стабильный ключ через `LLM_CACHE_KEY`. Bash доступен по флагу `--allow-shell` в доверенной рабочей папке на POSIX. Команды Bash имеют права запустившего процесс пользователя.

## Как устроена подгрузка

Chat Completions получает один и тот же набор из трёх шлюзов на каждом шаге.

| Шлюз | Что получает модель |
| --- | --- |
| `skill_list` | Имена и краткие описания доступных скиллов |
| `skill_load` | Инструкции и схемы выбранного скилла. Модуль импортируется при первой активации в процессе |
| `tool_run` | Результат вызова инструмента из активированного скилла |

По умолчанию доступен скилл `workspace` для чтения, записи и правки файлов. В Python новые скиллы регистрируются через `Agent(..., skills=[SkillSpec(...)])`. Доверенный модуль экспортирует `SKILL` с инструкциями и списком `ToolSpec`. Для модели каталог расширяется по мере необходимости без изменения массива `tools`.

## 1. Как сохранить Prompt Cache

Системное сообщение, исходная задача и порядок схем шлюзов фиксируются на весь запуск. Скилл приходит обычным результатом `skill_load` в конце истории. Между компактациями запросы только дописывают историю. Схемы активных скиллов можно запросить повторно, если их ответы выбыли из окна.

При превышении локального бюджета харнесс старается снизить вход до 80% доступного объёма. Он заменяет старые пакеты «ответ ассистента и все результаты его инструментов» одной структурированной сводкой после исходной задачи. Сводка хранит имена загруженных скиллов, точные контрольные данные из `workspace.checkpoint` и ограниченные выдержки из вызовов и результатов. Последние пакеты сохраняются целиком, пока помещаются. Оценка размера берётся из UTF-8 JSON, положительное расхождение с usage провайдера добавляется как запас. При явном отказе провайдера из-за контекста харнесс пробует ещё сократить историю и заново запросить модель.

Кэш зависит от точного общего префикса. Компактация сдвигает границу совпадения к неизменной части, после чего совпадение снова растёт с каждым добавленным ходом. Ключ может помочь маршрутизировать запросы у поддерживающего его провайдера. Достигнет ли сохранённый префикс минимальной длины для кэша, зависит от модели и сервера. Фактическое переиспользование проверяется по `usage.prompt_tokens_details.cached_tokens` и доле ответов с этим полем. [Документация OpenAI о Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching) · [Пример метрик Chat Completions](https://developers.openai.com/cookbook/examples/prompt_caching101).

Сводка формируется локально без запроса к модели, поэтому её построение потребляет ноль выходных токенов. Произвольные подробности могут выпасть из сводки. Состояние, нужное позднее, модель может сохранить через контрольную точку или в файл рабочей папки.

## 2. Какие ошибки возвращать модели

| Ситуация | Что делает харнесс |
| --- | --- |
| Невалидный JSON, неверный тип или аргумент, неизвестный инструмент, скилл ещё не загружен | Возвращает короткий структурированный результат с кодом и способом исправления |
| Файл отсутствует, путь вышел за границы папки, точная правка не совпала, команда завершилась с ненулевым кодом | Применяет проверки сам и возвращает модели причину. Модель может перечитать файл, выбрать допустимый путь или исправить команду |
| Таймаут Bash | Останавливает группу процессов и возвращает частичный вывод. Перед новым вызовом нужно проверить состояние файлов, поскольку команда могла успеть их изменить |
| Временная ошибка транспорта, 429 или временный 5xx при запросе к модели | Повторяет запрос к провайдеру с ограниченным backoff. Поддерживает `Retry-After` до 30 секунд. Вызванные инструменты не повторяются |
| Переполнение окна у провайдера | Компактирует собранный контекст и повторяет запрос, пока можно уменьшать запрос и есть попытки |
| Ошибка учётных данных, исчерпанная квота, повреждённый пакет вызовов или сбой самого инструмента | Завершает запуск с диагностическим статусом. Проверка всего пакета вызовов предшествует исполнению. Подробности исключений хоста не отправляются модели |

## Бенчмарк

```sh
python3 -m unittest discover -v
python3 -m benchmark --output benchmark/results.json
```

Задача состоит из 32 последовательных чтений и записей при миграции инвентаря и создания скрипта аудита. Проверяющий код сверяет содержимое всех файлов, исходные данные и три сценария запуска аудита. Последний шаг улучшенного цикла использует точные факты из первой контрольной точки, уже перемещённой в сводку.

| Цикл | Размер окна | Верные пакеты | Аудит | Запросы | Вход, оценка | Выход, оценка | Общий префикс, оценка |
| --- | ---: | ---: | --- | ---: | ---: | ---: | ---: |
| Исходный | 4 096 | 3/32 | Не пройден | 10 | 14 954 | 582 | 11 930 |
| Улучшенный | 4 096 | 32/32 | Пройден | 70 | 194 737 | 6 088 | 121 525 |
| Исходный с широким окном | 65 536 | 32/32 | Пройден | 69 | 886 959 | 5 192 | 861 324 |

При одинаковом окне исходный цикл получает отказ по контексту. Улучшенный завершает 32 пакета после 31 компактации без отказов. Среди завершившихся прогонов входной объём снизился на **78,04%**. В широком окне исходный цикл повторно использует больше префикса в симуляции. Поэтому сравнение объёма входа само по себе не измеряет стоимость или задержку.

Замеры получены из детерминированной имитации провайдера с реальными операциями в рабочей папке. Токены оцениваются по UTF-8 JSON, а переиспользование моделируется длиной общего префикса с предыдущим принятым запросом. Токены просуммированы по принятым ответам. Провайдер с реальной моделью в этом прогоне не использовался. Подробности и проверяемые условия сохранены в [результатах бенчмарка](benchmark/results.json).

Для запуска с реальным Chat Completions задайте `LLM_BASE_URL`, `LLM_MODEL` и при необходимости `LLM_API_KEY`. Передайте фактическое окно модели. Отчёт хранит usage провайдера, покрытие полей и локальную оценку отдельными полями.

```sh
python3 -m benchmark --live --context-window 8192 --output live-results.json
```
